# Data Integrity Audit

## 1. Financial Ledger, Invoicing & Payments

- **DI-01 Fixed (Double Invoicing & Cross-Customer Charge Linking)**: `InvoiceService.CreateDraftInvoiceAsync` and `InvoiceService.AddInvoiceItemAsync` now verify that any linked `ShipmentCharge` exists, belongs to the invoice's `CustomerId`, and is not already invoiced (`IsInvoiced || InvoiceId.HasValue`) before setting `IsInvoiced = true` and `Invoice` / `InvoiceId`.
- **DI-02 Fixed (`FinancialLedgerEntry.ReferenceId = 0` & User Impersonation Fallback)**: `PaymentService.RegisterPaymentAsync` previously posted payment ledger entries with `referenceId: 0` before `SaveChangesAsync()` and fell back to `UserAccounts.FirstAsync()` if `Username` did not resolve. Now wraps payment save, ledger posting, balance update, and initial allocations in an explicit relational transaction, persists `Payment` first so `ReferenceId == payment.Id`, and requires authenticated user resolution without arbitrary first-user fallback.

## 2. COD Lifecycle & Balance Consistency

- **DI-03 Fixed (Premature COD Holding Mutation & Missing Upper-Bound Check)**: `CodCollectionService.RecordCollectionAsync` previously modified `CustomerBalance.TotalCodHoldingAmount` regardless of collection status (causing double-counting once `VerifyCollectionAsync` later credited `TotalCodHoldingAmount`) and did not cap `CollectedAmount <= Shipment.CodAmount`. Now validates `0 <= CollectedAmount <= Shipment.CodAmount` and adjusts `TotalCodHoldingAmount` only when the collection is already `VerifiedByCashier`.
- **DI-04 Fixed (Unverified COD Remittance & Erroneous Status Promotion)**: `CodRemittanceService.CreateRemittanceAsync` and `AddItemAsync` previously allowed `CollectedByDriver` or `DepositedToBranch` collections to enter remittances, and `RemoveItemAsync`/`CancelRemittanceAsync` unconditionally set `Status = "VerifiedByCashier"`. Enforced `Status == "VerifiedByCashier"` on remittance creation/addition and restricted restoration to `"VerifiedByCashier"` only when `Status == "RemittedToCustomer"`.

## 3. Shipping, Carrier & Order State Machine Invariants

- **DI-05 Fixed (Order Cancellation vs In-Flight Shipments)**: `OrderService.CancelAsync` previously blocked cancellation only for `InTransit` or `Delivered` shipments, allowing confirmed orders with `PickedUp`, `InSortingHub`, `OutForDelivery`, or `Returning` shipments to be cancelled. Updated to block cancellation across all active/terminal physical shipping states.
- **DI-06 Fixed (POD Attempt Status & Return Transition Safety)**: `ProofOfDeliveryService.CreateAsync` now rejects non-`Delivered` attempts and validates `ShipmentStateHelper.IsValidTransition(..., "Delivered")`. `ReturnRequestService.ProcessAsync` now transitions shipments to `Returning` only when `ShipmentStateHelper.IsValidTransition(shipment.ShipmentStatus, "Returning")` is true.
- **DI-07 Fixed (Carrier Duplicate Booking & Sync Transition Bypasses)**: `CarrierIntegrationServiceImpl.BookShipmentAsync` rejects shipments with an existing `CarrierTrackingNumber` or terminal status. Both `CarrierWebhookServiceImpl` and `CarrierTrackingSyncOrchestrator` now apply `ShipmentStateHelper.IsValidTransition`, append immutable `ShipmentStatusHistory` entries, and emit `DeliveryCompletedIntegrationEvent` when transitioning to `Delivered`.

## 4. Inventory & Parcel Handling Atomicity

- **DI-08 Fixed (Reservation Consumption Integrity)**: `InventoryService.ConsumeReservationAsync` now runs in a relational transaction, rejects missing balances or insufficient `QuantityOnHand`/`QuantityAllocated` (removing `Math.Max(0, ...)` silent clamping), and resolves an actual `EmployeeId` instead of hardcoding `1`.
- **DI-09 Fixed (Swallowed Transitions & Missing Dispatch Item Deduction)**: `ParcelHandlingService.ReceiveParcelAsync` and `ConfirmDispatchAsync` now execute inside explicit relational transactions and propagate `TransitionStatusAsync` failures instead of logging warnings and saving split state. `ConfirmDispatchAsync` now deducts `InventoryBalances` and writes `InventoryTransaction` records for `DispatchItems`.
- **DI-10 Documented Schema Limitation (Adjustments & Transfers Headers Only)**: Because domain entities/tables `StockAdjustments` and `StockTransfers` contain header columns only (`StockAdjustmentItems`/`StockTransferItems` tables do not exist in SQL Server schema), `ApproveAdjustmentAsync` and `ConfirmTransferAsync`/`ReceiveTransferAsync` cannot compute per-SKU/location balance movements on approval/receipt without a schema migration. Added validation preventing identical source/destination warehouses and zero/negative quantities on `CreateTransferAsync`; full item-level workflow requires adding child item tables in a future release.
- **DI-11 Documented Partial Lot Key Limitation in Receipts**: `WarehouseIntegrationTests` creates a lot-numbered receipt (`LotNumber = "LOT-2026-A1"`) and subsequently reserves stock without specifying `LotId`. Changing `ConfirmReceiptAsync` to bind `InventoryBalance.LotId` without also relaxing reservation matching when `LotId == null` would break backward compatibility; left unchanged and documented for planned lot-allocation design.

## 5. Multi-Instance Concurrency & Sequences

- **DI-12 Fixed (`NumberSequenceService` Distributed Locking)**: Updated `NumberSequenceService.GetNextNumberAsync` to acquire SQL Server `UPDLOCK, ROWLOCK` row locks on `[configuration].[NumberSequences]` inside an explicit transaction when using SQL Server (verified with 12 concurrent tasks in `SqlServerHardeningIntegrationTests`). Note: `NumberSequence` initial row creation for an unseeded scope still relies on unique index enforcement if two processes initialize a brand-new scope simultaneously for the first time.
